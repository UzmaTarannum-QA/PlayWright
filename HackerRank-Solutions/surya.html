A field guide to non-blocking JavaScript

Six words that decide
what runs when.

JavaScript runs on a single thread, yet it juggles network calls, timers, and file reads without freezing the page. The trick isn't magic — it's a queueing system, and these six keywords are how you talk to it.

01

Function modifier

async

Placing async before a function declaration does two things: it makes the function always return a Promise, even if you just return a plain value, and it unlocks the use of await inside that function's body.

Think of it as a permission slip — await only works inside a function that's been marked async (or at the top level of a module).

  • Always returns a Promise. Returning 42 from an async function actually resolves a Promise with the value 42.
  • Errors become rejections. A thrown error inside an async function rejects the returned Promise instead of throwing synchronously.
  • Works on function declarations, expressions, arrow functions, and class/object methods.
async function getUser(id) {
  return { id, name: "Riya" };
}

getUser(1).then(user => {
  console.log(user); // { id: 1, name: "Riya" }
});

// getUser() itself returns a Promise,
// not the object directly.
console.log(getUser(1)); // Promise {<pending>}
Gotcha — calling an async function does not pause execution. It runs synchronously until the first await, then hands control back immediately.
02

Operator

await

await pauses execution of the surrounding async function until the Promise it's given settles, then unwraps it — returning the resolved value, or throwing the rejection reason as a regular exception you can catch with try/catch.

Crucially, it only blocks that one function. The rest of the program — the call stack, the UI, other code — keeps running.

  • Reads like sync code. That's the entire point: it replaces chained .then() calls with linear, top-to-bottom logic.
  • Pauses, doesn't block the thread. Control returns to the event loop while waiting.
  • Awaiting a non-Promise value just resolves immediately with that value.
async function loadProfile() {
  try {
    const res = await fetch("/api/user");
    const data = await res.json();
    console.log(data);
  } catch (err) {
    console.error("Failed to load:", err);
  }
}
Pattern — pair every await-heavy function with try/catch. It's the async equivalent of a Promise's .catch().
03

Constructor

new Promise()

A Promise is an object representing a value that isn't ready yet. You construct one with an executor function that receives two callbacks — resolve and reject — and you call whichever one fits once the async work finishes.

Every Promise sits in one of three states: pending, fulfilled, or rejected — and once it settles, it can never change state again.

  • Use this constructor to wrap callback-based APIs (timers, file reads, older libraries) into something await-able.
  • You rarely need new Promise() when calling modern APIs like fetch — they already return Promises.
  • Consumed with .then() / .catch(), or with await.
function wait(ms) {
  return new Promise((resolve, reject) => {
    if (ms < 0) {
      return reject(new Error("negative delay"));
    }
    setTimeout(() => resolve(`waited ${ms}ms`), ms);
  });
}

wait(500).then(console.log); // "waited 500ms"
Gotcha — forgetting to call resolve or reject leaves the Promise pending forever — a silent, hard-to-debug hang.
04

Static method

Promise.all()

Takes an array (or any iterable) of Promises and returns a single Promise that fulfills once every one of them fulfills, with an array of results in the same order you passed them in.

If any Promise rejects, the whole thing rejects immediately with that reason — the other Promises keep running, but their results are discarded.

  • Best for independent tasks you need all of before continuing — e.g. loading a user, their posts, and their settings together.
  • Fails fast: one rejection sinks the batch.
  • Want partial results even on failure? Use Promise.allSettled() instead.
const [user, posts, settings] = await Promise.all([
  fetch("/api/user").then(r => r.json()),
  fetch("/api/posts").then(r => r.json()),
  fetch("/api/settings").then(r => r.json()),
]);
// all three requests fire in parallel
05

Static method

Promise.race()

Also takes an array of Promises, but settles as soon as the first one settles — fulfilled or rejected — and ignores the rest. Whichever Promise crosses the finish line first decides the outcome.

  • Classic use case: timeouts. Race a real request against a timer Promise; whichever finishes first wins.
  • "Race" includes rejections — a fast failure beats a slow success.
  • Losing Promises aren't cancelled, they just get ignored — this doesn't stop network requests already in flight.
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timed out")), ms)
  );
  return Promise.race([promise, timeout]);
}

try {
  const data = await withTimeout(fetch("/slow"), 3000);
} catch (e) {
  console.error(e.message); // "timed out" if too slow
}
06

Static method

Promise.allSettled()

Like Promise.all(), but it never short-circuits. It waits for every Promise to settle — fulfilled or rejected — and resolves with an array describing each outcome individually. Nothing is ever discarded.

Each entry in the result array has a status of "fulfilled" or "rejected", plus either a value or a reason.

  • Use when partial failure is fine. You want to know what succeeded and what didn't, without one failure sinking the batch.
  • Added in ES2020 — specifically to fix Promise.all's fail-fast behavior when you don't want it.
  • Never rejects itself — the returned Promise always fulfills.
const results = await Promise.allSettled([
  fetch("/api/user").then(r => r.json()),
  fetch("/api/broken-endpoint").then(r => r.json()),
]);

results.forEach(r => {
  if (r.status === "fulfilled") {
    console.log("got:", r.value);
  } else {
    console.log("failed:", r.reason);
  }
});
Pattern — perfect for dashboards or batch jobs where one broken data source shouldn't take down the whole page.
07

Static method

Promise.any()

The optimistic sibling of race(): it resolves as soon as the first Promise fulfills — ignoring rejections along the way, unless every single Promise rejects.

If all Promises reject, it rejects with an AggregateError that bundles every individual rejection reason together.

  • Use for redundancy: hit several mirrors or servers at once, and take whichever responds successfully first.
  • Unlike race(), a fast failure does not win — only a fulfillment counts.
  • Also ES2021+; check runtime support in older environments.
try {
  const fastest = await Promise.any([
    fetch("https://mirror1.example/data"),
    fetch("https://mirror2.example/data"),
    fetch("https://mirror3.example/data"),
  ]);
  console.log("first successful mirror:", fastest.url);
} catch (err) {
  console.error("all mirrors failed:", err.errors);
}
Gotcha — don't confuse this with Promise.all. "Any" cares about the first success; "all" cares about every outcome.
08

Pattern, not syntax

Callback

The original async pattern: pass a function as an argument, and have the async operation call it back once it's done. No special keyword — just a function reference handed to another function.

Promises and async/await were built on top of this idea, largely to fix its readability problems.

  • Node.js convention: error-first callbacks — (err, data) => {} — check err before touching data.
  • Callback hell: nesting callbacks inside callbacks produces a rightward-drifting pyramid that's hard to read or refactor.
  • Still everywhere: event listeners (addEventListener), array methods (.map, .forEach), and older Node APIs all use callbacks.
// classic "callback hell"
getUser(id, (err, user) => {
  if (err) return handleError(err);
  getPosts(user.id, (err, posts) => {
    if (err) return handleError(err);
    renderPage(user, posts); // nesting deepens...
  });
});

// still a callback — just a clean one
button.addEventListener("click", () => {
  console.log("clicked");
});
Why it faded — error handling had to be repeated at every level, and execution order became hard to trace. Promises replaced nesting with chaining; async/await replaced chaining with plain sequential code.
